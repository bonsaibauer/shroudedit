# Anpassungen

## 2026-10-11 — API-Server: Hetzner CX23

Für den ersten API-Server wurde ein Hetzner Cloud CX23 eingerichtet. Die gebuchte Größe umfasst 2 vCPU, 4 GB RAM, 40 GB lokalen Datenträger und laut Bestellung 20 TB ausgehenden Traffic. Der angezeigte Preis beträgt 0,01 € pro Stunde beziehungsweise ungefähr 6,53 € pro Monat.

Der CX23 ist der zunächst geplante Hetzner-Host für die API. Die GitHub-Pipeline unterscheidet die Freigabeziele `dev` und `prod`. Das bedeutet noch nicht, dass auf Hetzner zwei vollständige Backend-Stacks laufen: Der Runtime-Deploy auf den Server ist noch nicht eingerichtet und muss passend zur gewünschten Serveraufteilung konfiguriert werden.

**Ressourcenhinweis:** Der CX23 ist ein kleiner Startserver. Der aktuelle `docker-compose.yml`-Stack startet neben Labrinth unter anderem PostgreSQL, Redis, ClickHouse, Redpanda und drei Elasticsearch-Knoten mit jeweils 512 MB Java-Heap. Dieser vollständige Entwicklungsstack ist für 4 GB RAM nicht als Produktionsdeployment geeignet. Vor dem API-Deployment müssen wir die Produktionsdienste gezielt auswählen beziehungsweise verwaltete Dienste verwenden und Elasticsearch/weitere nicht benötigte Entwicklungsdienste aus dem Startpfad nehmen. Datenbank-, Redis-, Such- oder sonstige Verwaltungsports dürfen nicht öffentlich erreichbar sein.

**ClickHouse-Konfiguration für Production noch offen:** Labrinth verwendet ohne explizite Umgebungsvariable den Datenbanknamen `staging_ariadne` (`apps/labrinth/src/env.rs`); auch die lokalen Compose-Umgebungen setzen diesen Namen. Die TTL-Sonderbehandlung in `apps/labrinth/src/clickhouse/mod.rs` prüft dagegen auf `staging_analytics`. Vor dem Produktivbetrieb muss die Production-Datenbank ausdrücklich festgelegt und die TTL-Regel mit diesem Namen abgeglichen werden. Der Server darf nicht versehentlich den Staging-Datenbanknamen als Production-Ziel übernehmen.

## 2026-10-11 — Deployment über Versions-Branches und PRs

Versions-Branches wie `1.0.0` sind Arbeits- und Versionsstände. Pushes auf diese Branches lösen keinen Deploy und keine Image-Veröffentlichung aus. Ein Pull Request aus einem Versions-Branch nach `dev` darf nach bestandenen Prüfungen die Dev-Umgebung aktualisieren. Ein separater Pull Request desselben, unveränderten Commits nach `prod` gibt Production frei. Der Workflow prüft, dass genau dieser Commit zuvor über einen gemergten PR in `dev` angekommen ist.

Die Workflows prüfen, dass PRs nach `dev` oder `prod` aus einem Branch im Format `X.Y.Z` kommen. Nach einem Merge wird ein eindeutiger Git-Tag nach dem Muster `v1.0.0-dev.<laufnummer>` beziehungsweise `v1.0.0-prod.<laufnummer>` erstellt. Die API- und Frontend-Builds verwenden dieselbe Tag-Berechnung und ergänzen jeweils einen SHA-Tag; ein Image wird nur gebaut, wenn der PR die zugehörigen Dateien ändert. Die Nummer ist keine separat gespeicherte Build-Zählung: Sie wird deterministisch aus der First-Parent-Position des gemergten Ziel-Commits abgeleitet. Damit erhalten Git-Tag und alle Images aus demselben PR dieselbe, eindeutige Nummer. Sie steigt bei jedem PR-Merge in den jeweiligen Zielbranch, auch wenn ein Teilprojekt wegen unveränderter Dateien kein Image baut; dadurch können in Image-Tags Nummernlücken entstehen. Das Ruleset erlaubt Merge- und Squash-Merges, sodass jeder PR-Merge genau einen First-Parent-Schritt hinzufügt; direkte Commits und Rebase-Merges sind gesperrt. Die unveränderlichen Versions- und SHA-Tags werden pro passendem PR-Merge veröffentlicht. `dev-latest` und `latest` werden getrennt aktualisiert, nachdem geprüft wurde, ob sich die relevanten API- beziehungsweise Frontend-Dateien seit diesem Merge geändert haben. Dadurch blockiert ein späterer, nur andere Bereiche ändernder PR die Alias-Aktualisierung nicht, und verspätete Workflows setzen keinen älteren relevanten Stand zurück. `dev-latest` zeigt auf den letzten Dev-Build; `latest` wird ausschließlich für Production aktualisiert. Der Cloudflare-Worker wird direkt aus dem Frontend-Repository mit der Umgebung `dev` und der Route `dev.shroudedit.com` deployt.

Die Dev-Website ist eine separate Frontend-Umgebung unter `dev.shroudedit.com`. Sie verwendet dieselben produktiven Dienste und Daten wie die Produktions-Website: Labrinth unter `api.shroudedit.com`, Archon unter `archon.shroudedit.com` und Shared Instances unter `shared-instances.shroudedit.com`. Änderungen an Daten über die Dev-Website wirken sich daher auf Production aus. Es werden keine separaten Dev-API-, Archon- oder Shared-Instances-Dienste vorausgesetzt; der nicht verwendete Frontend-Schalter für eine separate Dev-Archon-API wurde entfernt. Die Cloudflare-Deploy-Aktion verwendet die vorhandenen GitHub-Secrets `CF_API_TOKEN`, `CF_ACCOUNT_ID` und `SENTRY_AUTH_TOKEN`.

**GitHub-Ruleset importieren:** Die JSON-Datei [`docs/github-rulesets/protect-dev-prod.json`](github-rulesets/protect-dev-prod.json) schützt die Branches `dev` und `prod`. In GitHub im Repository `Settings → Rules → Rulesets → New ruleset → Import a ruleset` wählen, die JSON-Datei auswählen, Regeln prüfen und erstellen. Das Ruleset verlangt PRs sowie den Check `Version branch only`, verhindert Löschen und Force-Pushes und erlaubt keinen Bypass. Dafür braucht das GitHub-Konto Admin-Rechte oder die Berechtigung zum Bearbeiten von Repository-Regeln. Der Check validiert das Branch-Schema `X.Y.Z` und dass der Production-PR exakt den zuvor nach `dev` gemergten Commit verwendet. Falls GitHub den Check beim Import noch nicht erkennt, zuerst einen PR aus einem Versions-Branch nach `dev` öffnen, den Check ausführen lassen und danach das Ruleset importieren. GitHub beschreibt den [Ruleset-Import](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository#importing-a-ruleset) und die [verfügbaren Regeln](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

**Hetzner-Deploy noch nicht verdrahtet:** Das Repository enthält bislang nur den lokalen Entwicklungs-Stack in `docker-compose.yml`; eine Hetzner-Compose-Datei, produktive Service-Konfiguration und ein eingerichteter SSH-Deploypfad fehlen. Die neuen API-Workflows veröffentlichen daher Images, starten aber noch keine API-Container auf dem Server. Der Hetzner-Schritt kommt hinzu, sobald Compose-Zielpfad, Dienste und Serverzugang feststehen. Der CX23 mit 4 GB RAM kann nicht ohne Ressourcenkonzept zwei vollständige Backend-Stacks parallel betreiben.

## 2026-10-11 — ShroudEdit-Desktop-App-Build und Release entfernt

ShroudEdit entwickelt und veröffentlicht keine eigene Desktop-Fenster-App. Im Repository gab es keine `apps/app`- oder `apps/app-frontend`-Quellverzeichnisse mehr, aber die separaten GitHub-Actions `theseus-build.yml` und `theseus-release.yml` waren noch vorhanden und konnten weiterhin Desktop-Installationsdateien bauen, Releases erstellen und Updates in den ShroudEdit-App-Dateispeicher `launcher-files.shroudedit.com` hochladen. Beide Workflows wurden entfernt. API- und Website-Funktionen für OAuth, Mod- und Blueprint-Uploads, Downloads sowie externe Launcher bleiben bestehen; dazu zählt auch die geplante Integration mit dem separaten ShroudForge Launcher. Historische Download-Statistiken behalten ihre frühere Theseus-Kennung, damit bereits gespeicherte Auswertungen weiterhin zugeordnet werden.

## 2026-10-12 — Abschlussprüfung der Deploy- und Launcher-Pfade

Beim letzten CI-nahen Production-Frontend-Build antwortete `api.shroudedit.com` mit einer Cloudflare-Challenge. Dadurch schlug das Abrufen des Tag-/Statuszustands fehl und der absichtlich strenge Production-Build brach ab. Vor einer produktiven Frontend-Freigabe muss der Buildzugriff auf diesen API-Endpunkt funktionieren; die Fehlerprüfung sollte nicht entfernt werden, weil sie einen Deploy mit unvollständigem Seitenzustand verhindert.

Die API-Client-Anbindung an `launcher-meta.shroudedit.com` bleibt erhalten. Die separate `.github/workflows/daedalus-docker.yml` wurde nicht als ShroudEdit-Desktop-App-Release entfernt, weil sie auf den Launcher-Metadaten-Dienst zielt. Sie ist derzeit jedoch nicht funktionsfähig: `apps/daedalus_client`, `packages/daedalus` und das Cargo-Paket `daedalus_client` existieren nicht im Repository. Zusätzlich hört der Workflow auf Pushes zu `main`, während sein Deploy-Job `refs/heads/prod` verlangt. Der Workflow wurde deshalb nicht auf eine neue Branch- oder Serverstruktur umgestellt; vor einer Änderung muss geklärt werden, ob der externe Launcher-Metadaten-Dienst weiterhin aus diesem Repository gebaut werden soll.

Der separate Workflow `.github/workflows/api-client-release.yml` veröffentlicht weiterhin automatisch `@shroudedit/api-client` nach npm, wenn sich das Paket auf `main` ändert. Das ist ein Paket-Release für externe API-Clients und kein Website- oder Hetzner-Deploy; es bleibt wegen der Launcher-Integration erhalten. Falls `main` nicht mehr als Paket-Release-Zweig dienen soll, muss dieser Pfad separat umgestellt werden.

## 2026-10-11 — Cloudflare Workers Free: CPU-Limit

Die explizite Einstellung `limits.cpu_ms: 5000` wurde aus `apps/frontend/wrangler.jsonc` entfernt. Cloudflare hat den Deploy mit Fehler `100328` abgelehnt, weil der Workers-Free-Plan keine benutzerdefinierte CPU-Grenze unterstützt.

Der Worker verwendet damit das Standardlimit des Free-Plans: 10 ms CPU-Zeit pro Anfrage. Das ist reine Rechenzeit; Wartezeit auf Antworten anderer Server zählt nicht dazu. Überschreitet eine Anfrage die Grenze, kann Cloudflare sie zur Laufzeit abbrechen. Der Build selbst war erfolgreich; blockiert wurde die Bereitstellung.

Ein späterer Wechsel zum Workers-Paid-Plan ermöglicht eine höhere CPU-Grenze. Die aktuelle Preis- und Limitübersicht steht in der [Cloudflare-Dokumentation](https://developers.cloudflare.com/workers/platform/pricing/).

## 2026-10-11 — Labrinth-API: Uploadlimit für Cloudflare Free

Cloudflare Free begrenzt den Inhalt eines proxied HTTP-Requests auf 100 MB. Labrinth nimmt Versionsdateien über solche API-Requests entgegen; die bisherigen Limits von 256 MiB für `.sfbp` und 500 MiB für andere Versionsdateien lagen über dieser Grenze und konnten deshalb schon am Cloudflare-Proxy mit `413 Request Entity Too Large` abgewiesen werden.

Die bestehende Größenprüfung für `.sfbp`-, Mod- und Modpack-Dateien wurde auf 95 MiB gesetzt. Cloudflare zählt den vollständigen Request einschließlich Multipart-Formulardaten. Die vorhandene Labrinth-Prüfung gilt pro Datei; kleinere Speziallimits, zum Beispiel für Galeriebilder, bleiben bestehen. Details zum [Cloudflare-Uploadlimit](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/4xx-client-error/error-413/).
